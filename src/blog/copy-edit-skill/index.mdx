As a developer with a non-traditional background, previously doing freelance audio engineering gigs in New York City, I was eager to prove myself and demonstrate competence early in my software development career. One side effect of this eagerness and mild insecurity was a tendency to leave long code reviews explaining my position if I disagreed with someone’s code. My manager noticed, and one morning he arrived at the office with a stack of copies of [_On Writing Well_](https://www.harpercollins.com/products/on-writing-well-william-zinsser?variant=32118081159202), by William Zinsser, which he handed out to the entire team. I got the message.

This summer my team started a new project, making extensive use of Claude for code generation. After a few weeks of reviewing AI-generated code it became clear that, while excellent at coding, Claude currently lacks human judgement when it comes to writing code comments. Code submissions would often contain obvious and unnecessary statements, verbose prose, Claude-isms (“It’s not X, it’s Y”), and AI clichés (“The fix is simple — but the cause isn’t — and that’s the point.”)[^1]. If a pull request did not contain those tells, it was only because we’d put the effort in to clean them up before pushing the code.

Reviewing a coworker’s code one afternoon, I found myself once again commenting heavily on generated code comments, and I realized that we would likely have to keep policing these comments as long as we used Claude to develop. This wastes time and energy, and distracts the team from focusing on correctness and shipping features. I spent the rest of the day writing a Claude skill[^2] to impose some order on these AI-generated comments: [Copy Edit](https://github.com/focusconsulting/copy-edit-skill).

The skill consists of two components:

1. a [writing standard](https://github.com/focusconsulting/copy-edit-skill/blob/main/skills/copy-edit/standard.md), linked from our engineering constitution[^3], and
2. a linting step that runs at the end of any session where Claude generates code.

The writing standard is pulled into context and informs Claude’s general writing style across the entire codebase. Our engineering constitution contains a specific principle titled “Prose earns its keep” that lays out the basic rules: “Comments, docstrings, and prose documents carry only what the artifact itself cannot say: why, constraints, invariants, gotchas, regression records.” From there we link out to the standard, which goes into more detail and contains few-shot examples and guidelines.

The linting step is a guard against anything that might violate the standard. Over a long session the model tends to drift from the standard, and the linting step uses a fresh context window to analyze the diff. When Claude has finished coding, the skill pulls the diff, checks whether any changed line is prose for that file type, and if so hands the diff and the standard to a separate read-only agent. That agent evaluates new prose against the standard and returns suggestions rather than edits. The session that wrote the code reads this output and decides what to apply, then a small script applies the changes and logs the run.

Below are examples from the first sweep of the codebase. I’ve altered the domain to remove any contract-specific references.

## Results

So how did it turn out when we ran the Copy Edit skill on our entire codebase? The first run compressed comments up to ~50% across different sections of the app (e2e, app code, tests, templates). Since adopting it into our workflow, we have seen sustained reductions in comment density between 30% and 60% across those same categories[^4]. Granted, brevity is not the point, quality is. Post adoption, code review around comments has largely shifted from form to function. There have been no recent “Please shorten this” or “Is this comment necessary?” style reviews. Rather, reviews are now more likely to ask “Does this still hold?” or more often, “LGTM.”[^5]

You can check out the skill on GitHub: [focusconsulting/copy-edit-skill](https://github.com/focusconsulting/copy-edit-skill).
